2.4 ALTERNATIVA: fazer os 5 de uma vez com um laco no PowerShell.
    Execute a partir de ap003_microsservicos/

    $repo = "leoolivieri"
    $tag  = "1.0.0"
    $svcs = [ordered]@{
      "barramento"    = "ecm516-20262-barramento-de-eventos"
      "lembretes"     = "ecm516-20262-lembretes"
      "observacoes"   = "ecm516-20262-observacoes"
      "consulta"      = "ecm516-20262-consulta"
      "classificacao" = "ecm516-20262-classificacao"
    }
    foreach ($pasta in $svcs.Keys) {
      $img = "$repo/$($svcs[$pasta]):$tag"
      Write-Host "==> $img"
      docker build -t $img ".\$pasta"
      if ($?) { docker push $img }
    }

    Obs.: o PowerShell 5.1 nao aceita "&&"; por isso o "if ($?)".

2.5 Conferir que subiu:

 5. RICHARDSON NIVEL 3 (HATEOAS) - O QUE MUDAR EM CADA SERVICO
================================================================================

5.1 O MODELO DE MATURIDADE DE RICHARDSON, EM UMA LINHA CADA

    Nivel 0 - "pantano do POX": um unico endpoint, um unico verbo, o que
              fazer vai no corpo. HTTP e so transporte.
    Nivel 1 - RECURSOS: varias URIs, uma por recurso (/lembretes,
              /lembretes/1/observacoes).
    Nivel 2 - VERBOS HTTP e CODIGOS DE STATUS: GET le, POST cria, PUT
              atualiza, DELETE remove; 200, 201, 400, 404 com significado.
    Nivel 3 - CONTROLES DE HIPERMIDIA (HATEOAS): a resposta carrega os
              links das proximas acoes possiveis. O cliente navega pela API
              seguindo links, sem ter URLs fixas no codigo.

5.2 ONDE A SUA SOLUCAO ESTA HOJE

    Ja no nivel 2, com furos. Antes de dizer "nivel 3" feche os furos do
    nivel 2 (itens 5.4) e so depois acrescente os links (itens 5.5).

5.3 DECISAO DE PROJETO: como montar os links

    Um pod nao sabe qual e a URL publica dele. Resolva injetando as URLs
    por variavel de ambiente no Deployment - sem isso os links sairiam
    apontando para dentro do cluster e nao funcionariam no navegador.

    Variaveis a injetar (valores para o Docker Desktop):
      URL_LEMBRETES    = http://localhost:30000
      URL_OBSERVACOES  = http://localhost:30001
      URL_CONSULTA     = http://localhost:30002
      URL_BARRAMENTO   = http://ecm516-20262-barramento-de-eventos-service:10000

    No codigo, leia com valor padrao:
      const URL_LEMBRETES = process.env.URL_LEMBRETES || 'http://localhost:4000'

    Ganho extra: os enderecos deixam de estar fixos no codigo, o que era

5.5 ACRESCENTAR OS CONTROLES DE HIPERMIDIA

    Padronize o formato. Sugestao (estilo HAL, simples de justificar):
    cada recurso ganha um objeto "_links", onde cada chave e uma relacao
    (rel) e o valor tem "href" e "method".

    (a) [ARQ] lembretes/index.js - GET /lembretes (colecao)

        {
          "_links": {
            "self":     { "href": "http://localhost:30000/lembretes", "method": "GET" },
            "criar":    { "href": "http://localhost:30000/lembretes", "method": "POST" },
            "consulta": { "href": "http://localhost:30002/lembretes", "method": "GET" }
          },
          "itens": [
            {
              "id": 1,
              "texto": "Estudar Kubernetes",
              "_links": {
                "self":            { "href": "http://localhost:30000/lembretes/1", "method": "GET" },
                "observacoes":     { "href": "http://localhost:30001/lembretes/1/observacoes", "method": "GET" },
                "criarObservacao": { "href": "http://localhost:30001/lembretes/1/observacoes", "method": "POST" }
              }
            }
          ]
        }

        Repare que a colecao virou objeto com "itens". O formato antigo era
        um mapa {1: {...}, 2: {...}} e nao tinha onde pendurar os _links da
        colecao. Sugestao: escreva uma funcao unica
        montaLembrete(lembrete) que devolve o objeto ja com _links, e use
        ela no GET da colecao, no GET por id e no POST - assim o formato
        nunca divergir entre as rotas.

    (b) [ARQ] lembretes/index.js - GET /lembretes/:id
        Mesmo objeto do item da colecao, com _links.self e a relacao
        "colecao" apontando de volta para /lembretes.

    (c) [ARQ] lembretes/index.js - POST /lembretes
        HTTP 201 + Location + corpo com _links (self, observacoes,
        criarObservacao, colecao).

    (d) [ARQ] observacoes/index.js - GET /lembretes/:id/observacoes

        {
          "_links": {
            "self":     { "href": "http://localhost:30001/lembretes/1/observacoes", "method": "GET" },
            "criar":    { "href": "http://localhost:30001/lembretes/1/observacoes", "method": "POST" },
            "lembrete": { "href": "http://localhost:30000/lembretes/1", "method": "GET" }
          },
          "itens": [
            {
              "id": "uuid...",
              "texto": "revisar HATEOAS, isso e importante",
              "status": "importante",
              "_links": {
                "self":     { "href": "http://localhost:30001/lembretes/1/observacoes/uuid...", "method": "GET" },
                "lembrete": { "href": "http://localhost:30000/lembretes/1", "method": "GET" }
              }
            }
          ]
        }

    (e) [ARQ] observacoes/index.js - LINKS QUE DEPENDEM DO ESTADO
        Este e o ponto que separa "nivel 3 de verdade" de "nivel 2 com
        links decorativos". Monte os _links conforme o status:

          status "aguardando"  -> NAO inclua a relacao "reclassificar".
                                  Inclua a relacao "classificacao" apenas
                                  informando que o processamento esta em
                                  curso.
          status "importante"  -> inclua a relacao "reclassificar"
                 ou "normal"      (POST, reenviando para classificacao).

        Ou seja: o cliente descobre o que pode fazer lendo a resposta, nao
        consultando documentacao. Destaque isso no relatorio - e a
        definicao de HATEOAS.

    (f) [ARQ] consulta/index.js - GET /lembretes
        A base de leitura e agregada, entao ela e o melhor lugar para
        mostrar navegacao. Em cada lembrete inclua _links.self (no proprio
        consulta), e tambem "lembreteOriginal" (no servico de lembretes) e
        "observacoes" (no servico de observacoes). Assim o cliente entra
        pela consulta e chega aos servicos de escrita seguindo links.

    (g) OPCIONAL, mas rende pontos: crie GET / (raiz) em cada servico
        devolvendo so os _links de entrada da API - o "ponto de partida"
        que um cliente HATEOAS usa para se orientar. Exemplo para o
        servico de lembretes:

        {
          "_links": {
            "self":      { "href": "http://localhost:30000/", "method": "GET" },
            "lembretes": { "href": "http://localhost:30000/lembretes", "method": "GET" },
            "criar":     { "href": "http://localhost:30000/lembretes", "method": "POST" }
          }
        }

    (h) OPCIONAL: responder com Content-Type "application/hal+json" em vez
        de "application/json", deixando explicito o formato de hipermidia:
        res.type('application/hal+json')

 ANEXO B - INGRESS (OPCIONAL, MELHORA O HATEOAS)
================================================================================

Com NodePort cada servico tem uma porta diferente (30000, 30001, 30002), e
os links do nivel 3 ficam apontando para hosts diferentes. Funciona, mas
nao e elegante. Com um Ingress tudo fica sob http://localhost e os links
passam a ser caminhos do mesmo host - bem mais proximo do que se espera de
uma API HATEOAS.

B.1 Instalar o controlador nginx no Docker Desktop
    kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/main/deploy/static/provider/cloud/deploy.yaml
    kubectl get pods -n ingress-nginx
    (espere o pod do controller ficar Running)

B.2 [ARQ] implantacao/kubernetes/06-ingress.yml

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ecm516-20262-ingress
spec:
  ingressClassName: nginx
  rules:
    - host: localhost
      http:
        paths:
          - path: /api/lembretes
            pathType: Prefix
            backend:
              service:
                name: ecm516-20262-lembretes-clusterip-service
                port:
                  number: 4000
          - path: /api/observacoes
            pathType: Prefix
            backend:
              service:
                name: ecm516-20262-observacoes-clusterip-service
                port:
                  number: 5001
          - path: /api/consulta
            pathType: Prefix
            backend:
              service:
                name: ecm516-20262-consulta-clusterip-service
                port:
                  number: 6000

B.3 Se adotar o Ingress, as variaveis do item 5.3 mudam para:
      URL_LEMBRETES   = http://localhost/api/lembretes
      URL_OBSERVACOES = http://localhost/api/observacoes
      URL_CONSULTA    = http://localhost/api/consulta
    e voce provavelmente vai querer ajustar as rotas do Express para o
    prefixo /api/... (ou usar rewrite-target no Ingress).

B.4 Custo/beneficio: mais uma peca para instalar e depurar. Se o prazo
    estiver curto, entregue com NodePort e cite o Ingress no relatorio como
    evolucao possivel.
